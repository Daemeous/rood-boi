# The VRAM lane (T5): textures and palettes owned by the renderer, the CPU rasterizer retired

Status: DRAFT for the user's review, 2026-11-17. Design only; no code until it is reviewed. It covers tie T5 of
[PS1_Ties.md](../PS1_Ties.md), inside [the off-the-PS1 plan](2026-11-08-off-the-ps1.md), and builds on
[the T5 survey](2026-11-12-t5-vram-survey.md) (whose slices S0 to S3b are built; section 1.1 says what that left).
Numbers are measured on s2-frame fcea69fd3 (main b2e75c3b8 plus the T4 and T8 lanes), 2026-11-17. Sizes are rough agent
time, calibrated on the memory lane's measured rates (a proven step costs 1 to 1.5 hours of wall time whatever its size).

## 0. The short version

- Today the game's textures, palettes and frame buffers live in one 1024 x 512 array of 16-bit pixels. Since the survey
  the renderer no longer reads that array: it owns a copy (`rvram`) built from an ordered event stream (uploads, fills,
  copies, read-back fences), and with the defaults (`pc_native_room` and `pc_native_actors` 2) the CPU rasterizer
  already draws only the 2D. What is left tying the game to the array is small and listable: 12 game read-back sites,
  8 files that read texels to recognise images, the CPU rasterizer and its stale-area machinery, and the tests that
  use the null renderer's CPU frame as a picture.
- The target: the renderer owns textures, palettes and render targets as resources and the game only issues
  operations on them (upload, fill, copy, palette write, capture, restore). The game side keeps one transfer-only
  mirror of VRAM as saved state (snapshots, rewind and the content readers need a byte image); it is not a yardstick.
- The CPU rasterizer goes in one step (T5-6), after everything that needs its pixels has moved. That step is also
  where the proof changes from "the CPU frame is the original's" to "our own previous build" (section 3).
- Eight steps, each one provable with the usual lanes; the first two only count and fence (sections 4 and 5).

## 1. What touches VRAM today

### 1.1 Built already (survey S0 to S3b, 2026-11-12 to 11-14)

- `pc/src/boot_runtime.c`: the game's array (`vram`, :22) and the stream: every write the game makes (LoadImage,
  ClearImage, MoveImage, copy items, resync) is an event; `ROOD_VRAM_STREAM_CHECK=1` replays the stream into a shadow array
  and compares it with the game's every vsync (0 differing pixels on 25 routes).
- `pc/src/gpu_hw.c`: the renderer's own VRAM (`rvram`) written by those events only; its texels feed the R16UI texture
  (`pc/src/vk_hw.c:263`, `VK_FORMAT_R16_UINT` 1024 x 512) and every renderer-side lookup (UI text, upscale, replay undo).
  The CPU rasterizer's pixels reach it as posted rectangles (`pc_hw_mark_raster` / `rvram_apply`: hundreds per frame).
- Read-backs are stream events too: `store` (StoreImage) and `texture` (a primitive sampling the frame being drawn);
  on the 25 routes only `texture` ever copies back (map 2, storage 2, manual 1, setup 13, score 8 per run).
- Screen copies sample a render-target capture, not VRAM (`WINDOW_CAPTURE`, `pc_vk_hw_capture`): the menus' cross-fades,
  the map's darkening, the ending's dissolves.
- The renderer thread (`render_thread 2`) consumes the stream; it is the reason the stream exists.

### 1.4 What still needs the CPU rasterizer (the honest list)

Under the defaults it no longer draws the room, the characters, their shadows or the particles (native lists draw
them; `scene_smoke` says "the CPU frame holds the 2D only"). What still reads its pixels:

1. the three frame readers (TITLE, MENU5, MENU7) and the `texture` fences (map, storage, manual, setup, score): these
   read or sample frame pixels the rasterizer drew; every one becomes a capture (T5-4);
2. the null renderer's picture (`build_compare --renderer null` hashes the CPU frame; `classic_parity` compares
   packets and items, not pixels, and does not need it);
3. the software present path and the movies' 24-bit display;
4. the OpenGL fallback (frozen): it presents through the same hardware path, so it keeps working only while the
   hardware path does not need the CPU frame (question 1 in section 7);
5. the oracle digest's VRAM pages (the frame area is in the hashed range).

Nothing in the game's logic reads the CPU frame except the 9 frame readers, which is why the retirement is a test and
tool problem more than a game one.

## 2. The target

### 2.1 Resources and operations

The renderer owns three kinds of resource; the game names them with the words it already writes into packets and
items (the tpage word, the CLUT word, the rectangle), and the renderer resolves a word to the resource that is current
at that point of the stream:

| Resource | What it holds | Created and changed by |
|---|---|---|
| texture page area | a 64 x 256 (4-bit) / 128 x 256 (8-bit) / 256 x 256 (15-bit) view of VRAM pixels in the form the sampler wants | upload, fill, copy (a new version of the destination) |
| palette | one CLUT row (16 or 256 entries) | palette write (the CLUT commit, `loadClut`, the fades), upload into a CLUT row |
| render target | the frame area (the display buffers) at the target's resolution, plus its captures | draw; capture (save a rectangle), restore (draw a capture back), copy |

Operations are the events of the stream with their meaning made explicit: `upload`, `fill`, `copy`, `palette_write`,
`capture`, `restore` (and `resync`, the whole-state event for snapshots). A draw refers to resources by their
versions, so a copy between two draws is exact by construction (the stream already orders them; the version makes
it checkable: the stream check reports a draw that samples a region written after the draw's position).

The first form keeps the shader and the R16UI texture: the resource table is a bookkeeping layer over `rvram`
(versions, roles, dirty ranges) and is where captures, palettes and copies stop being "writes to a rectangle of an
array". The second form (T5-7) replaces the array by real resources: texture pages decoded at upload into a form the
shader samples directly, palettes as small textures indexed by the CLUT word, the frame area as render targets. The
form change is a renderer-internal step behind the operations, provable by frames.

### 2.2 What stays on the game side

One transfer-only mirror of VRAM (a 1 MB array written only by the same operations on the game thread), as the
survey proposed. It is saved state, exact for texture and CLUT areas because only transfers write them, and it is
what every content reader, the snapshot, rewind and the digest keep using. The frame area of the mirror is not
exact once the CPU rasterizer is gone (it holds what transfers put there, not what was drawn); nothing reads it
(T5-4 and T5-5 first). The mirror goes when files are decoded into assets (memory lane S6, T9): textures then enter as
asset ids and the content readers key on them instead of on texel hashes. That is outside this lane.

### 2.3 Palette animation as an operation

A palette write names the rows it changes. Today a commit re-uploads a 7 KB block and the renderer re-uploads the
whole 64 x 256 tile and re-derives anything keyed on the texels (materials, emissive reads, UI text identification).
As an operation, the renderer updates the palette rows only, and anything keyed on a palette hash is invalidated by
row. The fades (`_loadClutTransition`) change rows every frame for a few seconds; room fades, the title and the ending
are the routes that show it.

### 2.4 Captures

The 9 frame readers are pairs: `StoreImage` of a frame rectangle into a heap buffer, later `LoadImage` of the same
buffer (the backup and restore of a screen under a fade or a file menu). A capture pair keeps the pixels on the GPU:
the store registers a capture for that buffer address and size; the matching load draws the capture back. The
buffer's contents are filled by a read-back only if the game reads them in between (any other access of that buffer is
a fence: the fallback is today's read-back, so nothing is wrong when a pair is not recognised). The glyph-cell readers
(2 files) read texels, not the frame: they read the mirror.

## 3. The yardstick: where the proof switches

What "identical to the original" rests on today:

- the game array holds what the original's VRAM would: transfers exactly, and the 2D as the CPU rasterizer draws it
  (the rasterizer is the PS1's GPU, bit for bit for the primitives the game uses);
- the oracle digest hashes VRAM pages across a replay; `build_compare --renderer null` and the null lanes hash the CPU
  frame;
- every other lane (Vulkan frames, casts, rooms, menus) already compares our new build with our previous one.

Steps T5-0 to T5-5 keep the yardstick intact: they change where data lives and who reads it, never what is drawn, and
each is proved by frames 0 differ **and** the CPU frame and VRAM digest 0 differ against the previous build.

The stream digest (`build_compare --vram-stream`, RPC `vram_stream`) is part of that proof; it is a running digest from the start of a
route, and the story routes restart it at the replay's first frame (`vram_stream {reset}`, commit 1cad4844d: the way to a story scene is unpaced and
not the same twice, the replay is). With that, the `--vram-stream` lane is 0 differ old against old on the 13 routes.

Where the CPU frame stood as a lane: T5-0 to T5-3 were proved with the null renderer's CPU frame (`build_compare --renderer null`) 0 differ against the
previous build. T5-5 (2026-11-18) makes the null renderer draw no pixels, so from T5-5 that lane hashes the drawing stream's chain (the items the game made), and
the last build whose null renderer rasterized is the reference build: tag `t5-last-cpu-frame` (4af64bc28), its binary kept in `wip/t4/ref-4af64bc28`. T5-5 is
proved against it by the stream chain (equal: the items are unchanged), the Vulkan lanes and full classic_parity.

The switch is at T5-6, the commit that deletes the CPU rasterizer, and exactly there:

1. Before T5-6: the last build that has the rasterizer is tagged (commit id in this document and the binary kept in
   `wip/`): the *last reference build*. Its CPU frames of the null lanes and its VRAM digests are the final proof
   that the 2D equals the original's drawing.
2. T5-6 is proved against that build: Vulkan frames 0 differ on every lane, the items stream digest equal (T5-5
   introduces it), and the oracle's VRAM digest equal over the transfer areas (texture and CLUT pages); the frame
   area is dropped from the digest's ranges in the same commit and the commit says so.
3. After T5-6 the only yardstick is the previous build (`build_compare`, `classic_parity` on items): the claim "the
   2D frame equals the original's" is last checked at the reference build and is transitive afterwards (a chain of
   0-differ steps). The null renderer is "no pixels": the game runs and the items are produced; it is not a picture.
4. Anything that needs a pixel-exact reference of the original after T5-6 (a new 2D primitive path, a mask-bit
   question) is settled from the reference build's binary, which stays kept.

**Revision 2026-11-17 (after T5-0 and T5-1, agreed with the coordinator): T5-2 is not a step; the order is T5-0, T5-1, T5-3, T5-4, T5-5, T5-6,
T5-7.** The reconnaissance for T5-2 found nothing to build that a proof could show:

- The renderer already tracks dirtiness per 16-row band (`dirty_bands`, `gpu_hw.c`: bit b of a tile column's word is rows 16 b to 16 b + 15). A
  256 x 14 CLUT commit dirties one band in each of 4 tile columns; the 64 x 256 tile re-upload this document assumed does not happen.
- The caches that key on palette content (`ui_text.c`, `emissive.cpp`) are not invalidated by VRAM writes: they key on the content and on
  `pc_ui_text_generation` (a setting's change), so there is no over-invalidation to remove.
- Only two game sites are pure palette writes: `vs_main_commitClut` (the 256 x 14 block at (768, 224), when `uploadPending`) and `vs_main_loadClut`
  (slot >= 14). The other CLUT loads are generic TIM `LoadImage` calls into arbitrary rows.
- The census (section 8) counts 6,328 uploads over the four CLUT cells (768..1023, 192..255) across 25 routes of about 65,000 vsyncs: about one commit
  per 10 vsyncs, mostly the fades.

Palette writes become real operations in T5-7, where a palette is a resource (a small texture indexed by the CLUT word) and a commit updates its
rows; until then an upload into a CLUT row is an upload. The copies are where the cost is: the census counts 7,322 and 3,700 copy events into
(640, 0) and (704, 0) and 1,000 to 5,000 per block out of (640..960, 256..448) (the actors' texture-map frames and the room's animated textures),
each a CPU copy in `rvram` followed by a band re-upload; T5-3 makes them GPU-side copies with versions and is the next step, then T5-4 (captures).

**Revision 2 (2026-11-17, T5-4 reconnaissance): T5-4 is not capture pairs; it reduces to three read-backs and goes into T5-6.** The "9 frame readers"
are not what section 1.3 said. Read in place (`TITLE 22C.c`, `MENU5 4D8.c`, `MENU7 260.c`) and against the census:

- MENU7's two reads are a CLUT row (`clutBuf`, `StoreImage` at `260.c:3563`) and a helper that reads a rectangle the caller names; neither is a frame.
- MENU5 backs up two rectangles before it loads the map background over them: the CLUT row (768, 227) and (672, 256, 96 x 240); only the second is
  a frame area (the census counts 11 to 86 rasterized rectangles in each of its blocks in the map route).
- TITLE reads four rectangles: (192, 448) and (352, 448) (160 x 64 each, menu strips: transfer-only blocks, 0 rasterized) and (678, 376, 180 x 24) and
  (688, 256, 160 x 128) (the drawn title picture: 11,928 to 17,496 rasterized rectangles per block, the display covers them). The game then
  *computes on the pixels* (`_fadeInMenu` blends the bitmaps it read and uploads the result), so a capture handle that keeps the pixels on the GPU cannot
  replace the read: the game needs the values.

So of the 9, 3 read pixels the CPU rasterizer drew (TITLE's two, MENU5's second) and 6 read transfer-only areas, which are exact in the mirror
whatever happens to the rasterizer. A StoreImage of a frame area is already a fence that copies the render target back into the game's array
(`pc_hw_sync`, `sync_kinds`); it stays exactly that after the rasterizer goes: the read-back writes the target's pixels into the mirror's frame area at the
fence, as a transfer event, and the game reads them. The frame area of the mirror is then "what read-backs put there", which is what section 2.2 says.
What the retirement needs is therefore not a new operation but the guarantee that the three sites, the movie display, RPC screenshots and the
checkpoints are the only readers of the frame area, which T5-0 to T5-1 and the stream check give (the census shows the frame blocks read by
nothing else). The `texture` fences (`pc_hw_sync_texture`: map 2, storage 2, manual 1, setup 13, score 8 per run) exist only because the CPU rasterizer samples a
frame pixel; the GPU path samples the capture (`WINDOW_CAPTURE`), so they go with the rasterizer in T5-6.

The order is now T5-0, T5-1, T5-3 (done), T5-5 (the null renderer as "no pixels" and the tests off the CPU frame), T5-6 (the rasterizer: the proof switch),
T5-7. T5-5 is the long step: seven test files and the build_compare null lanes hash the CPU frame (section 1.3).

Total: about 14 to 19 agent days if every step proves clean; the long pole is T5-7, and T5-0 to T5-6 stand alone and
free the CPU frame, the stale machinery and the test coupling without it. The estimates are ranges, not measurements;
the measured floor is 1.5 hours per proven commit.

### T5-6 as built (2026-11-19; the proof is pending the landing run)

What the step does, as code: the walk's commands (`boot_gpu_polygons.inc`, `boot_gpu_lines.inc`, the rectangle case in `boot_runtime.c`) parse and hand over
as before and draw nothing; `pixel()`, `texture()`, the fill loops of the rasterizer, the raster marks and posts (`pc_hwc_mark_raster`, `pc_hwc_raster_post`,
`C_MARK_RASTER`, `C_RASTER_POST`, `pc_hw_raster_skip`, `ROOD_RASTER_SKIP`), `ROOD_NULL_RASTER`, the software presenter (the 640 x 480 SDL surface;
`ROOD_RENDERER=software|x11` are gone; a machine without Vulkan or OpenGL does not start), `ROOD_SCALE=0` (is 1), the stream checker's feedback counters and the
frame-cost raster counters are deleted, with `gpu_probe` (it tested nothing but the rasterizer). What stays is the read-back, because the game still reads the frame in
three places (TITLE's two rectangles, MENU5's one), a sprite can sample the frame, and screenshots and checkpoints show it.

The read-back is the old stale-area model with one change: **every primitive now leaves its drawing area stale** (`MISSING`: the game's VRAM lacks what the renderer
drew), not only what a native list covered. The producer marks at the record (`pc_hw_triangle_decide` for triangles and, through the same decision, for rectangles; a
line marks when it is recorded) and the renderer marks the same set when it applies the record (`decision->mark`, `pc_hw_mark_drawn`); the existing fences (StoreImage
`pc_hw_sync_store`, `pc_hw_sync_texture`, own copies, screenshot and checkpoint `pc_hw_sync`) copy the target back where something reads it. The renderer's own VRAM copy
(`rvram`) therefore gets its frame area from read-backs only. The stale list is eight rectangles (a full list merges into a bounding box: a superset is safe, the target
holds the same words as the array wherever nothing was drawn; it costs a bigger read-back, which is the thing to watch in the proof's read-back counts).

The oracle digest (`snapshot.c`, RPC digest, the `vram` field) now hashes the game's array without the cells a primitive drew in (`pc_vram_transfer_digest`: 64 x 16 cells,
set by every drawn primitive's pixels inside its drawing area, cleared when a transfer covers the cell whole, host state): **the frame area is out of the digest's
ranges in this commit**, and the transfer areas are proved by the stream chain (`vram_stream`) being equal to the reference build's, since the whole-array digests
of the two builds cannot be equal (the reference's holds the CPU frame). The census's "raster" kind now counts the renderer's drawn rectangles.

**What the proof changed (2026-11-19 and 20; the design above is what is built).**
- The stale areas are a bitmap of 64 x 16 cells (MISSING and PLACED), not rectangle lists: a read-back clears exactly the cells it read, so a partial read leaves the rest and nothing merges or is lost (a list of 8, then of 64 rectangles, fragmented and looped).
- A draw that samples a stale area takes **GPU own copies always** (`pc_hw_sync_texture`, `pc_hwr_texture_stale`): the target is the truth, and a read-back per sampling draw stalled the renderer. Texture fences on the storage screen: 32,817 (every drawn cell read back) to 0; the reference had 2 at 4:3 and 36,756 at 16:9.
- A screenshot or checkpoint is a **capture** (`PC_RQ_CAPTURE`): the rectangle asked for, one blit of that extent (the driver's nearest blit places its samples by the extent: 64 x 224 against 320 x 224 differ in 1,903 channel values), no overlay bake, no stale area touched. The comparison tool takes no screenshots in `--present` mode: a screenshot bakes the held text overlay where a stale area is read and so disturbs the build that has one.
- Held text a screen copy needs in the rows it copies is drawn into the target for the read and taken out again (`own_apply`, Vulkan: `pc_vk_hw_scratch`, colour only, so the G-buffer and depth are untouched; checked byte-equal on storage: 202 of 202), so the picture shown keeps its text live. Storage bakes on the displayed target equal the reference's at every moderate sample.
- The VRAM stream digest no longer mixes fence events (reads): the stream's non-fence events are identical in order, rectangle, draw count and payload to the reference's over a whole storage route (5,878 events).
- The comparison against the previous build is on the presented picture (`build_compare --present`). **The accepted class** (the user, 2026-11-19): text edges in screen-copied panels (title, storage, data, status, the memory-card screens), the map's faint blue backdrop tint, and a one-step (1/255) dark-glow strip. These are textures sampled from a drawn area: the reference sampled the CPU rasterizer's PS1 pixels there, now it is the target's own picture. Anything outside that class (fights, rooms, casts, 3D areas) is a regression: fight, rooms, casts and the multisample fight (`aa msaa2+fxaa`, `render_thread 2`) show 0 differences.

### T5-7 interface sketch: the texture and palette provider (2026-11-23, agreed with the coordinator)

The renderer and every content system see textures as **handles**, not as VRAM coordinates. This is the "texture and palette provider" of port-kit's
rendering model: another game implements the same handles (Kagero: native textures, so a handle is an asset and its version never moves; PS2: GS memory,
so a handle is a block of GS memory and an upload or a copy bumps it). The PS1 adapter is the implementation in this tree; the (tpage, clut, u, v) decode
(`pc_tex_index`, `pc_tex_colour`, `vram_texels.h`) is its internals and stays inside it.

```c
typedef struct { uint32_t id; uint32_t version; } pc_tex_handle;       /* id: opaque, stable while the resource exists (0: none);
                                                                          version: bumped when its contents change by upload, fill, copy or read-back */
typedef enum { PC_TEX_INDEXED4, PC_TEX_INDEXED8, PC_TEX_DIRECT16 } pc_tex_mode;
typedef struct {            /* what one draw samples: the renderer's only view of a texture */
    pc_tex_handle page;     /* the texture page resource */
    pc_tex_handle palette;  /* the palette resource (none for DIRECT16) */
    pc_tex_mode   mode;
    int           box[4];   /* u0, v0, u1, v1 of the texels the draw reaches (inclusive), in the page */
    unsigned      window;   /* the page's texture window (mask and offset), 0 for none */
} pc_tex_sampling;

/* the adapter's side (the PS1 one reads the words a primitive carries) */
pc_tex_sampling pc_tex_describe(unsigned tpage, unsigned clut, unsigned window, const int uv_box[4]);
pc_tex_handle   pc_tex_page_handle(unsigned tpage);                   /* the page's current handle */
pc_tex_handle   pc_tex_palette_handle(unsigned tpage, unsigned clut);
int             pc_tex_current(pc_tex_handle h);                      /* h.version still the resource's */
/* content (for materials, emissive, UI text recognition): materials never decode VRAM themselves */
size_t          pc_tex_box_indices(const pc_tex_sampling*, uint16_t* out, size_t max);   /* the page's raw texels (indices or colours) of the box, row by row */
size_t          pc_tex_palette_colours(const pc_tex_sampling*, uint16_t* out, size_t max);/* the palette's entries as 15-bit colours */
/* a lookup the adapter keeps, keyed by (page id, page version, palette id, palette version, box): the same sampling gives the same answer until a version moves */
const pc_tex_content* pc_tex_content_of(const pc_tex_sampling*);      /* indices key, palette key, 'opaque', 'size' ... computed once per version */
```

Versions are what replace the tile-dirty notifications (`pc_ui_upscale_tiles_changed`, `pc_emissive_vram_dirty`, `pc_screen_owner_vram_changed`): a cache keyed on a
handle's version is invalid exactly when the resource it names changed, not whenever a 64 x 256 tile near it did.

**7a, as a plan.** (1) the PS1 adapter: page and palette handles over the renderer's VRAM, versions kept per 64 x 16 cell (a write bumps the cells it covers; a
page's or palette's version is the highest of its cells, so a CLUT commit next to a page does not move the page), hooked at the renderer's write points
(`rvram_put`, `rvram_copy`, the read-backs); (2) `pc_tex_describe` at the draw's own words; (3) the content systems read through
`pc_tex_box_indices` / `pc_tex_palette_colours` and key their caches on versions; (4) the shader and the R16UI texture are untouched behind it (the switch of 7b).
Proof at each step: the fight and menus lanes identical against s9-null, content counters equal, classic_parity on Vulkan.

### T5-7b design (2026-11-23): the shaders read the resources

Where the shaders read VRAM today (Vulkan): `vram.glsl` (`fetch`, `texel_at`: window, depth, CLUT) included by `hw_frag.glsl` (the packet path) and `native_frag.glsl` (the native lists); 
`emissive.glsl`, `rt_common.glsl`, `probe_bvh.glsl`, `text_dist.glsl`, `dof.glsl` fetch it too. The image is one R16_UINT 1024 x 512 (`vk_hw.vram`, binding 0 / 2), kept current by
band uploads from the renderer's copy (`pc_vk_hw_upload_rects`), by GPU own copies of the render target where a draw samples the frame (`own_apply`), and by
`vram_from_target`. So "the sampled copy" is not the renderer's `rvram`: it holds target pixels where draws sampled the frame, which versions do not see.

Form: two array textures. Page layers: R16_UINT 256 x 256, one layer per (page x, page y, mode) = 32 pages x 3 modes (4-bit and 8-bit layers hold the CLUT index per texel, 15-bit
layers the colour), 96 layers, 12.6 MB. Palette layers: R16_UINT 256 x 1, allocated on demand per palette handle (16 or 256 entries), found through a small table
(clut word -> layer) in a uniform/storage buffer. A draw's state already carries tpage, CLUT and window; the shader derives the layer from them (`page_layer(tpage)`,
`palette_layer(clut, mode)`), so the vertex format does not change. `texel_at` becomes: apply the window, fetch the index from the page layer at (u, v), look it up in the palette layer.

Filling: a compute pass decodes pages and palettes from the sampled copy (`vk_hw.vram`) into the layers when their handle's version moved since the layer was filled (the renderer
knows the versions at `rvram_put`/`rvram_copy` and the draw's sampling at `pc_tex_describe`); a page that lies over the frame area, or any page a draw samples through an own copy,
is refilled at that draw (the frame is live: versions do not move when the GPU draws), so the first slices keep these on the old path. That is the hybrid: a per-draw flag
(`page is a pure upload page`) chooses the resource path or the VRAM path; with the switch off (`ROOD_TEX_RESOURCES=0`, and in the first slice by default) every draw takes the VRAM path.

Slices (each provable by frames 0 differ against the previous build, same lanes as 7a):
1. the resource images and their fill pass (compute decode from `vk_hw.vram`), the layer/palette tables, the version bookkeeping, nothing sampling them yet (a debug check compares every
   layer with `texel_at` over the VRAM image at the frame boundary: 0 differing texels over the routes).
2. `hw_frag` and `native_frag` read the resources behind the switch for pure upload pages; frames 0 differ with the switch on and off.
3. the other readers (emissive, rt_common, probe_bvh, text_dist, dof): their `texel_at` goes through the same function; then the switch is on by default.
4. what the resource form buys: only the changed pages are uploaded/decoded (no band uploads of the whole VRAM), palette animation updates a 256 x 1 layer, and a texture-provider implementation can fill the layers from native textures.
**Built, slices 1 and 2 (2026-11-23).** `tex_pages`, `tex_palettes`, `tex_table` in `vk_hw.c`; `gpu_hw.c` "the texture resources" (`tex_note`: the draw's sampling, the page layer and palette slot refilled from
the renderer's VRAM when their handle's version moved, after a `flush()` so what is batched samples them as it was; a draw whose pages lie under an own copy of the frame is not a pure-upload draw and stays on the VRAM image);
`hw_frag.glsl` reads them for draws flagged `WINDOW_RESOURCE` (`tex_resources.glsl`: `texel_choice`, the one place the two paths meet). The flag is stripped from recorded replays and held text (they draw later).
`ROOD_TEX_RESOURCES=1` turns it on (off by default for now); `ROOD_TEX_CHECK=1` compares every box a draw samples with the sampled copy of VRAM (`tex_resources_smoke`: 7,041 boxes, 24.6 M texels, 0 differ; 30,696 draws read the resources).
With the switch on: fight, menus 4:3 and 16:9, casts and nine fence routes 0 differ against the build without it. **Slice 3 (2026-11-23):** the native lists read them too: `draw_native` asks `tex_list_pure` (a walk of the list's polygons' pages, `render_list_pages`: every page and palette current and none under an own copy of the frame) and flags the list's window word `WINDOW_RESOURCE`; `native_frag.glsl` uses `texel_choice`. Replays and interpolated lists keep the VRAM image. The switch is **on by default** now (`ROOD_TEX_RESOURCES=0` turns it off).
**Slice 4 (2026-11-23, branch vram-7b-rt):** the ray readers read them too. The resources moved into the VRAM image itself, below the VRAM rectangle (`vk_hw.h`: `VK_TEX_PAGES_Y`, `VK_TEX_PALETTES_Y`, `VK_TEX_TABLE_Y`; the image is 3072 x 4096), so every pipeline that binds `vram` reaches them: the three extra bindings in the seven pipeline sets (and the draw sets' own three) are gone, not added. `tex_pages.glsl` holds `texel_page` (the resource path's one lookup, shared with `tex_resources.glsl`). A triangle's page word carries `TPAGE_RESOURCE` (bit 15) when `pc_tex_resource_for(tpage, clut)` (gpu_hw.c: `tex_ensure` over the whole page) found its page and palette pure-upload and current at pack time (`ptgi.c rt_tpage`, used by `add_triangle` and by the animated-UV update); `surface_texel` in `rt_common.glsl` and `probe_bvh.glsl` takes `texel_page` for a flagged triangle and the VRAM path otherwise. The scene is cached across frames, so the pairs a flag was given for are remembered (an 8192-slot table, `tex_rt_key`) and `pc_tex_resources_refresh` brings every one up to date at the top of `vrt_room` (the entry of the path tracer, probes, particles and fog volume dispatches); before each dispatch `pc_tex_resources_refresh` brings the VRAM image up to date (`flush`, `upload_all_dirty`: what a draw has not yet sampled, an own copy of the frame given back), so a flagged and an unflagged triangle read the renderer's copy as it is now. (Slice 4 first kept the rays' old lag, a VALID row marking layers the image lacked invalid; branch gi-current removed the lag and the row. Setup route with GI on: 81 of 987 frames differ from before, 651 pixels in all, one level each.) Movers: `pc_vk_movers` flags an instance when every polygon's page and palette (as `rt_skin.comp` forms them) are resources; the skin pass writes the bit through a push constant. The VRAM path stays for unflagged triangles (replays, held text, anything not pure): when frame-sampling draws move to captures the choice in both shaders is deleted, as for the draws.
Risk: windows and wrap (`texel_at`'s window arithmetic moves unchanged into the new function); 16-bit pages whose 256-wide extent wraps the VRAM edge (x 960) are decoded with the wrap; the frame-area pages stay hybrid until the capture form of T5-4 exists.

### T5 capture step: the game's frame reads (2026-11-24, branch t5-capture from t5-7c)

target holds, and they go when the sprite that samples a drawn area samples a capture instead (the frame-sampling draws of the hybrid, the step after 7b's), not before: the bitmap is already a draw-area

## 6. Risks

- **Palette animation.** A CLUT row is written while sprites that use it were drawn earlier in the same frame: the
  stream's order is the guarantee, the version check proves it. Fades write rows every frame; the materials, the
  emissive and the UI text identification are keyed on palette content and must be invalidated by row (T5-2 lists the
  keys: `emissive.cpp` and `ui_text.c` caches, the material-map hash). A missed invalidation shows as one frame of the
  wrong colour; the fade routes are the proof.
- **Texture windows and wrap.** GP0 E2 (mask and offset of the U and V coordinates) and the 256-pixel wrap act on
  the texture page; the CPU does it in `texture()` (`boot_runtime.c:1324`), the shader in 26 places of `gpu_hw.c`. A
  resource per page must keep the wrap and the window exact; T5-7b is where it can go wrong, and `texture_window`
  is the first thing its proof covers (a test route that sets windows: the room's water and the title's clouds).
- **Frame-buffer effects.** Primitives that sample the frame being drawn (map darkening, ripples, the ending's
  dissolves, the file menus' rows): the capture form exists (`WINDOW_CAPTURE`), the `texture` fences are what is left;
  the quantisation of a read-back (5 bits per channel, mask bit from alpha) means a read-back is GPU dependent today
  and captures make that better, but any frame where a capture and a read-back disagreed by one level shows in the
  pair routes (the T4 comparison already tolerates levels in `cutscene_viewer_smoke`).
- **Save states and rewind.** The mirror is the saved truth; the renderer's resources are caches rebuilt by the
  `resync` event on restore. The frame area of the mirror is not exact after T5-6 (snapshot, rewind and `engine_rewind`
  must not compare it: the digest ranges change in T5-6 and the commit says so). Restoring mid-frame keeps the stream
  position as it is today. A captured screen held by a pair (a fade under way) must be in the snapshot: the capture
  pair table is saved state or the pair falls back to a read-back at snapshot time.
- **Movies and the 24-bit display.** Movie frames are LoadImage of MDEC output into the frame area; the 24-bit
  display reads the array as bytes. They go to the render-target form in T5-4's neighbour (a movie's frame is an
  upload into a render target); check ending and the opening on every step after T5-3.
- **Render thread.** Every operation is a stream event; fences are the only waits (`store`, `texture`, now captures).
  T5-4 removes most of them; a pair that falls back to a read-back is a visible hitch and the counters show it.
- **Tools that name VRAM positions.** Materials, the editor view and the emissive reads key on (tpage, CLUT, UV box)
  and the texel hash; T5-1 puts them behind one accessor so T5-7's version keys change one file.
- **Hidden readers.** 43 files mention `vram`. The stream check (0 differing pixels on 25 routes) proves writers;
  readers are closed by T5-1 (the accessor) and flushed by T5-6 (the compile error is the census).
- **Windows.** The Windows build is a gate on every step; it runs the same Vulkan resource code.

## 7. Decisions (the user's review, 2026-11-17)

All five proposals are decided as proposed:

1. **OpenGL.** Retired together with the rasterizer if it needs the CPU frame. T5-0 checks whether it does (whether
   `gl_present.c` or the GL hardware path reads the game's array or the CPU frame) and the commit that finds out says so;
   if it does not, it stays untouched by T5-6.
2. **The null renderer.** At T5-5 it becomes "no pixels, items only": the game runs and the items are produced, nothing is
   rasterized. The quick CPU lane of `verify.sh` stays; the tests that hashed its frame hash the items stream.
3. **The reference build.** The last build that has the rasterizer is kept as a binary in `wip/`, named by its commit, plus
   a git tag, until the lane after T5 has landed; then only the tag is kept.
4. **The mirror and the content readers.** The readers use texel hashes now (T5-1's accessor); they move to asset ids when
   files decode into assets (memory lane S6, T9).
5. **Order.** T5-7 (the real resources) comes after T5-6, not in parallel, so the stale machinery is not rewritten twice.
